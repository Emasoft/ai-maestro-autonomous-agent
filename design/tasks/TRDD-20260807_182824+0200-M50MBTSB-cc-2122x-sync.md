## What changed and why

### 1. The 200-spawn per-session cap is GONE (2.1.224) — a doc fact I authored went false

`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` (200, added 2.1.212) was removed:
*"long-running sessions no longer refuse new agents (concurrency and depth limits
still apply)"*. I had documented it as a live ceiling in **two** places during the
previous sweep — `README.md` and the persona's fan-out budget paragraph.

**Why it matters beyond accuracy:** this is the rare changelog entry that makes an
unattended run *less* safe. The cap was the thing that converted a runaway delegation
loop into a hard stop; with it gone, nothing bounds total spawns and `/clear` no longer
has a spawn budget to reset. Both surfaces now say the budget discipline is the agent's
to keep, not the host's to enforce.

### 2. Cross-session `SendMessage` + `ListAgents` (2.1.224) — a second transport R6 does not see

The host can now message *any* Claude Code session on *any* of the user's machines,
with `ListAgents` for discovery, and `crossSessionInbound` / `dialogExpiry` governing
delivery. 2.1.222 additionally routes such sends through the permission classifier.

The plugin had **zero** coverage of this — no mention of `SendMessage`, `ListAgents`,
or cross-session anything. That is a governance hole with a specific shape:

- It is **NOT** R42 keystroke injection (it delivers a message, not input into another
  session's prompt), so the existing absolute ban does not reach it — and saying it did
  would teach a false ban on a legitimate channel.
- But **R6 constrains the RECIPIENT, not the transport.** The host cannot see the R6
  graph, so it will cheerfully deliver a message the AI Maestro server would have
  rejected with `title_communication_forbidden`. An agent could therefore route around
  R6 without ever touching R42.
- The tool's own contract already forbids **permission laundering** — asking a peer
  session to do what was denied here. That is now stated in the persona, because a
  per-session permission decision is exactly what a cross-machine channel can quietly
  defeat.

### 3. Worktree isolation widened again (2.1.222)

The 2.1.216 fix (already cited in FORBIDDEN ACTION 1) left whole session kinds able to
run destructive git against the main checkout; 2.1.222 extends isolation to **file edits
and Bash in every session type**. Noted, with the standing caution that a host guard is a
backstop for the case we missed, never the reason our own rule exists.

## Guards added (the point of the exercise)

`test_readme_documents_the_unattended_session_caps` was **strengthened**: it previously
asserted only that `CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION` was *mentioned*, so it kept
passing after the underlying fact flipped. It now requires the README to state the cap
was removed in 2.1.224 AND to not present `(200 spawns` as current.

`test_persona_governs_the_host_cross_session_send_message_channel` is **new**: it pins
the recipient-not-transport rule, the anti-laundering clause, and the explicit
"NOT R42 keystroke injection" distinction.

**Lesson this repeats for the third time this week:** a test that pins a literal string
cannot tell you the string became false. Both times the suite stayed green while a doc
went stale. Guards on changelog-derived facts must assert the *claim*, not the *token*.
