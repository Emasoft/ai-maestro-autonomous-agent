## Changes landed (8 pins, all header-verified)

**`agents/ai-maestro-autonomous-agent-main-agent.md`**

1. **Arrival is not reading** (2.1.247) — an inbound peer message now collapses to a
   one-line `Message from @<sender>: <first line>` preview, expanded only with Ctrl+O.
   Added to the "a send is NOT a delivery" ladder: the recipient's human sees the FIRST
   LINE and nothing else, so the ask must stand alone in line one; and an inbound YOU
   receive may itself be a truncated preview, so expand before concluding what was asked.
   Axis: identity/addressing (the blind-spot question, not one of the four).
2. **A sub-agent that returns is not necessarily one that finished** (2.1.246) — a
   `maxTurns` stop now returns output MARKED PARTIAL with a hint to continue via
   `SendMessage`. Added beside the existing "never trust a fork's self-report" rule:
   check for the marker, and CONTINUE rather than re-spawn. Axis: sub-agent propagation.
3. **A model pin is no longer a guarantee** (2.1.247 + 2.1.243) — a sub-agent whose
   pinned model 404s on first call no longer dies; it falls back to the SESSION's model
   chain and runs anyway, so a cheap-model spawn can silently execute on the expensive
   one. The error now names type/status/request-id/model, and 2.1.243 added the model
   *and effort* each sub-agent actually ran on to `/tasks` — recorded as the place to
   verify a pin held. Axis: sub-agent propagation + token economy.

**`README.md`** (unattended survival)

4. **A silent session now fails loudly** (2.1.243) — an API request that never starts
   answering used to leave the session silent 10+ minutes with nothing to retry; it now
   times out at ~3 min, retries once, then surfaces `API Error: No response from API`.
   Converts the worst unattended failure mode (indistinguishable from working) into
   something `CLAUDE_CODE_RETRY_WATCHDOG` can act on. Paired with 2.1.246's auto-continue
   of a mid-stream cutoff in non-interactive sessions.
5. **Auto-compact moved later on the 1M window** (2.1.247) — Sonnet 5 now compacts at
   ~967K instead of ~934K, so a run carries ~33K more context before the compaction it
   plans around, and a handoff written "just before compaction" fires later than it used to.

**`skills/ai-maestro-autonomous-workspace-isolation/SKILL.md`**

6. **`/cd` does not move your scope, but it does change what governs you** (2.1.246) —
   the new directory's project settings, hooks, `.mcp.json` servers (behind the usual
   approval prompt), skills and agents now take effect immediately instead of waiting for
   `--resume`. Writable roots are absolute and unaffected; what changes is the governing
   config, so a "no hooks are configured here" conclusion must not be carried across a
   directory move. Axis: write scope.

## Verified absent (proven per entry, not assumed)

- **plugin.json BOM** (2.1.246) — `.claude-plugin/plugin.json` starts `7b 0a 20`, no BOM.
- **Skill name prefix doubling** (2.1.246) — only one of three SKILL.md files carries a
  frontmatter `name:`, and it is the unprefixed `ai-maestro-autonomous-prrd-trdd-kanban`,
  so no `/plugin:plugin:skill` doubling is possible.
- **All hook-related entries** (2.1.243 hook `if` conditions, 2.1.246 `${CLAUDE_PLUGIN_ROOT}`
  in hook errors, 2.1.247 hook output overflow) — `hooks/hooks.json` is `{"hooks": {}}`.
  Re-checked this pass rather than remembered, per the sync rule.
- **`skills/*/SKILL.md` discovery** (2.1.246 `/reload-plugins` reporting 0 skills) — this
  plugin does use that layout, and the host is past the fix at 2.1.247.

  This one needed a second pass. None of the three skills appear in the sweeping
  session's skill menu, which I first rationalized as consistent with "the host is past
  the fix" — but being past the fix predicts they SHOULD be listed, so that was a
  falsified prediction filed as a confirmation. The actual account, from
  `~/.claude/plugins/installed_plugins.json` (the authoritative install record) rather
  than from any single inference:

  - Both install records for `ai-maestro-autonomous-agent@ai-maestro-plugins` are
    `scope: local` and bound to OTHER projects — `projectPath: ~/agents/frank` (v1.6.22)
    and `projectPath: /private/tmp/pintest` (v1.6.13). Neither is this repo, which is the
    plugin's SOURCE tree and carries no install record at all.
  - In `~/.claude/settings.json`, `enabledPlugins` has 75 entries in **three** states:
    37 `true`, **38 `false`**, and — for this plugin — ABSENT. `ai-maestro-janitor` is
    `true` there, which is why janitor loads in this session while its own local records
    also point at other project paths.

  So the plugin contributes nothing HERE because it has no user-scope enablement and its
  local installs belong to other projects. That explains all three skills, including
  `ai-maestro-autonomous-prrd-trdd-kanban`, the one that DOES declare a frontmatter
  `name:`. Nothing in the plugin is broken.

  **This session's skill/agent menu is therefore not a valid observation surface for this
  plugin, and will not be until it is enabled here.** A future sweep that reasons "the
  host is past fix X, so these skills should now appear" is querying a surface that
  structurally cannot answer. Relatedly, none of the 8 pins below were validated against a
  RUNNING instance — they are changelog-verified only, which is correct for a docs sweep,
  but local observation can neither confirm nor falsify the persona edits while the plugin
  stays disabled here.

  Two signals that first looked like contradictions, both explained: `~/.claude.json`
  carries `.pluginUsage.ai-maestro-autonomous-agent@…` with `usageCount: 0` — a usage
  record, not an enablement record; and the perfect-skill-suggester hook can surface
  `ai-maestro-autonomous-agent:…-main-agent` because its own catalog CONTAINS the agent
  (100 "autonomous" hits in `skill-index.json`, 8 in `pss-skill-index.db`) while the host
  has not loaded it here — sufficient to explain the suggestion, and not a claim about how
  that catalog is designed.

  **Autopsy — this passage was wrong twice before landing, in the same shape both times.**
  v1 said "absent entirely — not disabled, never listed", from `ai-maestro-autonomous-agent`
  missing from `enabledPlugins`. v2 corrected the fact but invented a general rule to
  explain it — "that dict records only ENABLED plugins" — which is FALSE: 38 of its 75
  entries are `false`. The real distinction is **absent vs `false`**: an explicit `false`
  is a human's decision to disable, while ABSENCE means no user-scope decision was ever
  recorded, and only the install record says where the plugin actually lives. Each wrong
  version pointed at the right conclusion, which is precisely what made them dangerous —
  a negative lookup of unestablished scope reads exactly like a positive test, and an
  explanation invented to fit an observation is not evidence for it. Ask the artifact that
  OWNS the state (`installed_plugins.json`, `claude plugin list`), not one dict what it
  was told, and never generalize a format's semantics from a single absence.

  Separate and still open: `ai-maestro-autonomous-governance` and
  `ai-maestro-autonomous-workspace-isolation` declare neither `name:` nor
  `user-invocable:`, while every skill of the sibling `ai-maestro-plugin` declares both.
  That is a real frontmatter inconsistency, but it is NOT the cause of the absence above
  and there is no evidence it breaks loading — the repo's own test derives skill identity
  from the directory name. Recorded, deliberately NOT "fixed": the enablement test
  disproved the hypothesis that would have motivated the edit.

## Deliberately not done

- **Auto-mode entries** (2.1.246 `/permissions` Auto mode tab; 2.1.247 one-keystroke
  "Yes, and switch to auto mode" on Bash prompts; 2.1.243 availability fixes). The
  keystroke shortcut is a real approval-provenance surface — a single key changes the
  session's authorization posture — but this persona already governs provenance by
  requiring a quotable inbound authorization, which auto mode cannot manufacture. Adding
  a rule per host approval affordance would grow the persona without changing a decision.
  Revisit if auto mode ever becomes able to approve something the persona reserves.
- **Bash allow-rule wildcard warning** (2.1.246, `Bash(git * main)` also matching options
  inserted before the subcommand). Genuinely a security finding, but this plugin ships no
  allow rules — `hooks/hooks.json` is empty and the skills' `allowed-tools` use the
  narrow `Bash(git:*)` form, which the warning does not cover. Recorded, not acted on.
- **`promptCacheTtl` / `subagentPromptCacheTtl`** (2.1.243). Settings the launching
  environment owns, not the persona; the token-economy guidance already says to prefer
  bounded fresh agents over marathon context, which these do not change.
